Here are the parts that matter for your project, in order of how soon you'll hit them.

## 1. The mental model

JPA keeps a **persistence context**, a notebook of the entities it has loaded or saved inside the current transaction.

- **Loading** (`findById`) reads a row, builds the object, and writes it in the notebook.
- **Changing** a loaded entity (`account.setStatus(...)`) needs no `save`. At commit, JPA compares each object with its notebook copy and writes an `UPDATE` for whatever changed. This is called **dirty checking**.
- **Flush** means "send the pending SQL to the database now". It happens at commit, before some queries, or when you call `saveAndFlush`.
- **Outside a transaction** there is no notebook that lasts. Each repository call opens and closes its own.

## 2. Entity states (what `save` does)

| State | Meaning |
|---|---|
| New | an object you built with `new`, which JPA doesn't know yet |
| Managed | in the notebook, so changes are tracked |
| Detached | was managed, but the transaction ended |

**A gotcha with your design:** your ids are assigned in Java, not generated by the database. For an entity with an assigned id, `save()` can't tell new from existing, so it first runs a `SELECT` to check, then the `INSERT`. It works, but it's an extra query per insert. Two ways around it: ignore it for now, or have the entity implement `Persistable<UUID>` so it can say "I'm new" itself. For your ledger, ignore it until it matters.

## 3. Mapping details you'll need

```java
@Column(name = "created_at", insertable = false, updatable = false)   // database fills it
private Instant createdAt;

@Enumerated(EnumType.STRING)        // stores the text, never the number
private AccountStatus status;
```

- `Long` for `BIGINT`, `UUID` for `UUID`, `Instant` for `TIMESTAMPTZ`, `String` for `VARCHAR`.
- A nullable column needs a nullable Java type (`Long`, not `long`). Your `debits` and `credits` are nullable, so use `Long`.
- `nullable = false` and `length` are only used by `validate` and for documentation. Your real protection is the database.
- **Relationships (`@ManyToOne`) are optional.** For `Entry`, you can keep `private UUID accountId;` instead of a link to an `Account` object. For a ledger this is simpler and avoids surprise queries. Add relationships only when you see the need.

## 4. Derived query keywords

The method name is the query. A few you may use:

```java
Optional<Account> findByName(String name);
List<Account> findByStatus(AccountStatus status);
List<Entry> findByAccountIdOrderByCreatedAtDesc(UUID accountId);
boolean existsByName(String name);
long countByTransactionId(UUID transactionId);
```

- `And`, `Or`, `OrderBy...Desc`, `Between`, `In`, `IsNull` also work.
- Field names, never column names.
- Past about two conditions, write a `@Query` instead.

## 5. Your own SQL

```java
@Query(value = """
        SELECT COALESCE(SUM(e.credits), 0) - COALESCE(SUM(e.debits), 0)
        FROM entries e WHERE e.account_id = :accountId
        """, nativeQuery = true)
long creditMinusDebit(@Param("accountId") UUID accountId);
```

- `nativeQuery = true` is real Postgres SQL, with table and column names.
- Without it, you write JPQL, which uses entity and field names. Native is closer to what you already know.
- `:name` placeholders pair with `@Param`.

## 6. Locking (your payer lock)

JPA has its own lock annotation, `@Lock(LockModeType.PESSIMISTIC_WRITE)`, but it generates `FOR UPDATE`. Your design needs `FOR NO KEY UPDATE`, so write it as a native query:

```java
@Query(value = "SELECT id FROM accounts WHERE id = :id FOR NO KEY UPDATE", nativeQuery = true)
Optional<UUID> lockById(@Param("id") UUID id);
```

A lock only lasts while the transaction is open, so this must be called inside a `@Transactional` method.

## 7. Transactions with JPA

```java
@Service
public class LedgerService {
    @Transactional                      // one BEGIN ... COMMIT around the whole method
    public Result post(PostRequest request) { ... }
}
```

- Any `RuntimeException` thrown inside causes a rollback. A checked exception does not, unless you ask for it.
- Self-calls skip the proxy, so `@Transactional` has no effect on a method called from another method of the same class. That's why your retry loop lives in a separate class.
- After a failed statement, the transaction is dead and every later query fails until rollback.

## 8. Exceptions you'll meet

| Exception | Usually means |
|---|---|
| `DataIntegrityViolationException` | a constraint or trigger rejected the write (unique, CHECK, your triggers) |
| `CannotAcquireLockException` | deadlock or lock timeout, so your retry case (Postgres error `40P01`) |
| `JpaSystemException` | other database errors, sometimes wrapping a trigger's message |

To see what the database really said, look at the cause chain: `getMostSpecificCause()`.

## 9. Pitfalls for this project

- **Never let JPA send `created_at`.** Keep it read-only, or the sealed-transaction trigger rejects every payment.
- **`ddl-auto=validate` only checks entities against tables.** It never changes the schema, which is what you want.
- **JPA can issue an `UPDATE` with every column** if the others aren't marked `updatable = false`. That's why `Account` has those flags.
- **Turn on `spring.jpa.show-sql=true` while learning**, so you can see every statement your code causes.
- **Don't return entities from controllers forever.** The response DTO exists for that.

2. `save`, `findById` and one derived query.
3. `@Transactional`, so a failure rolls everything back.
4. Native `@Query` for the lock and the balance.
